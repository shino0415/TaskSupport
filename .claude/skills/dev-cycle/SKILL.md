name: dev-cycle
description: プランナー→ジェネレーター→セキュリティエバリュエーター→性能エバリュエーターの開発サイクルを、spec.mdのタスクを1つずつ回す。機能追加のプロンプト（例:「〜という機能を追加したい」）や、単に開発を進めたい旨の依頼を受け取ったときに使う。タスクが完了するたびに要約を提示し、オーケストレーターがローカルにgit commitしてから、承認は待たずに残タスクが尽きるまで自動で回り続ける。設計判断（複数の妥当な選択肢がある事項）と差し戻し上限到達時はサブエージェントに決めさせず、必ずAskUserQuestionでユーザーに委ねる。git push/docker push/実際のデプロイコマンドの実行は一切行わない。
---

このスキルは、`.claude/agents/`にある4つのサブエージェント（`planner` / `generator` / `security-evaluator` / `performance-evaluator`）を、spec.md駆動で1タスクずつ回すための手順です。あなた（オーケストレーター）はこの手順に従い、Agentツールで各サブエージェントを`subagent_type`指定で順番に呼び出してください。

## サイクル全体の流れ

```
ユーザーの依頼（新機能 / 「開発を進めて」等）
    │
    ▼
spec.mdに「## 実装タスク」が無い、または新機能の依頼か？
    │ Yes                              │ No（既存タスクの続きを進める）
    ▼                                  │
[planner] タスクをspec.mdに追記        │
    │  ＋「## 未決定事項」を記録          │
    ▼                                  │
「## 未決定事項」が未解決のまま残っているか？
    │ Yes → 【設計判断をユーザーに確認】（選択肢をAskUserQuestionで提示→spec.mdに反映）
    ▼ No
    └──────────────┬───────────────────┘
                    ▼
        spec.mdに status:未着手（または差し戻された修正待ち）のタスクがあるか？
                    │ No → ユーザーに完了を報告して終了
                    ▼ Yes
            [generator] タスクを1つだけ実装
                    │
                    ├─ 設計判断で行き詰まった → status: 要人間判断 → 【設計判断をユーザーに確認】へ
                    ▼ 実装完了（status: セキュリティ評価待ち）
            [security-evaluator]  セキュリティレビュー
                    │
                    ├─ Critical/High相当あり → status: 修正待ち、差し戻し回数+1
                    │       ├─ 差し戻し回数 < 5 → generatorに差し戻し（フィードバック付き）
                    │       └─ 差し戻し回数 = 5 → status: 要人間判断 → 【人間に相談】へ
                    ▼ 問題なし（status: 性能評価待ち）
            [performance-evaluator]  pytest/ruffで動作確認
                    │
                    ├─ 不合格 → status: 修正待ち、差し戻し回数+1
                    │       ├─ 差し戻し回数 < 5 → generatorに差し戻し（フィードバック付き）
                    │       └─ 差し戻し回数 = 5 → status: 要人間判断 → 【人間に相談】へ
                    ▼ 合格（status: 完了）
            【要約をユーザーに提示（非ブロッキング）】
                    │
                    ▼
            オーケストレーターが git commit（push はしない）
                    │
                    └─ 承認を待たずに次の 未着手 タスクへ（generatorへ戻る）
                       ※ユーザーが割り込みで差し戻しを指示した場合のみ、修正指示を添えてgeneratorへ（差し戻し回数にはカウントしない）
```

## 実行手順

1. **プランナー呼び出しの判定**: `spec.md`を読み、`## 実装タスク`セクションが無い（初回）、またはユーザーが新機能・大きな仕様変更を依頼している場合のみ、`subagent_type: "planner"`でAgentを呼ぶ（フォアグラウンド、`run_in_background: false`）。単に「既存タスクの続きを進めて」という依頼の場合はplannerを呼ばずスキップする。

2. **設計判断の確認**: `spec.md`の`## 未決定事項（要ユーザー判断）`に未解決の項目があれば、タスクループに入る前に解消する。
   - 各決定事項について、plannerが記録した選択肢をそのままAskUserQuestionの選択肢として提示する（要約・改変しない。ユーザーが選んでいない前提を混ぜない）。
   - ユーザーの回答をあなた自身が`spec.md`に反映する（決定事項を確定として書き込み、`## 未決定事項`からは解決済みとして除去または取り消し線を引く）。
   - その決定を待っていた`status: 要人間判断`のタスクを`未着手`に戻す。
   - これは差し戻し回数にはカウントしない。

3. **タスクループ**: `spec.md`を読み、`status: 未着手`（または差し戻し後の`修正待ち`）のタスクが残っている間、以下を繰り返す。すべて`run_in_background: false`で、前のステップの結果に依存するため並列には走らせない。
   a. `subagent_type: "generator"`でAgentを呼び、「spec.mdの次の未着手（または修正待ちの）タスクを1つ実装してください」と伝える。修正待ちの場合はフィードバック内容も伝える。
      - generatorが`status: 要人間判断`で戻ってきた場合（設計判断で行き詰まった場合）、報告された選択肢を使って手順2と同じ要領でAskUserQuestionをその場で行い、`spec.md`に決定を反映してから同じタスクでgeneratorを再度呼ぶ。これは差し戻し回数にカウントしない。
   b. `subagent_type: "security-evaluator"`でAgentを呼び、「直近でgeneratorが実装したタスクをセキュリティレビューしてください」と伝える。
      - `status: 修正待ち`になった場合、差し戻し回数が5未満なら(a)のgeneratorに戻る。5に達していたら**タスクを飛ばさず**、その場でループを止めて【人間に相談】（手順5）に進む。
   c. `status: 性能評価待ち`になったら、`subagent_type: "performance-evaluator"`でAgentを呼び、「直近のタスクをpytestで検証してください」と伝える。
      - `status: 修正待ち`になった場合、差し戻し回数が5未満なら(a)のgeneratorに戻る。5に達していたら【人間に相談】（手順5）に進む。
   d. `status: 完了`になったら、そのタスクについて手順4（要約提示・commit）を行い、承認を待たずに次の`未着手`（または`修正待ち`）タスクがあればそのまま手順3(a)に戻る。無ければ手順6（終了報告）に進む。

4. **完了報告とcommit（タスクが完了するたびに毎回・非ブロッキング）**:
   a. 次を要約してユーザーに提示する。承認や返答を待たず、そのまま次に進む。
      - 実装した機能の要約
      - セキュリティエバリュエーターの指摘内容（あれば、無ければ「指摘なし」）
      - pytestの実行結果（成功件数、lintの結果）
      - `spec.md`のどのタスクが`完了`になったか
   b. オーケストレーター自身が`git commit`する。
      - `git add`で変更ファイル（アプリコード・テスト・`spec.md`等）をステージする。
      - 完了したタスク内容が分かる日本語のコミットメッセージを付ける（既存コミットの文体に合わせる。例: 「〇〇エンドポイントを実装」）。
      - **`git push`は絶対に実行しない。**
   c. ユーザーが割り込みで差し戻しやその他の指示を送ってきた場合のみ、その指示を添えて(a)のgeneratorに戻る（このやり取りは差し戻し回数にはカウントしない＝無制限）。指示が無ければ自動的に次の`未着手`タスクへ進む。

5. **【人間に相談】（自動差し戻し上限到達時）**: `status: 要人間判断`になったタスクのうち、評価NGの5回差し戻し上限に達したものについて、これまでのセキュリティ/性能フィードバックの全履歴を要約し、ユーザーに方針を確認する（例: 要件を緩めるか、別アプローチを指示するか、手動で介入するか）。ユーザーの指示を得てから、必要ならgeneratorに新たな指示を添えて再開する。（設計判断待ちの`要人間判断`は手順2/3aで扱うので、ここでは扱わない）

6. **サイクル終了報告**: `spec.md`に`status: 未着手`（または`修正待ち`）のタスクが無くなったら、今回のオーケストレーションで完了した全タスクを要約してユーザーに報告し、終了する。

## 注意事項

- 1回のオーケストレーションで暴走的に多数のタスクを生成しないよう、plannerにはユーザーが依頼した範囲のみを仕様化させる。
- 各サブエージェントの最終報告はユーザーに直接は見えないため、サイクルの節目（各タスク完了時、要人間判断時、全体終了時）でオーケストレーターが要点をユーザー向けに日本語で要約すること。
- **`git commit`**: 手順4bでオーケストレーターがタスク完了ごとに自動実行してよい（ユーザー許可済み、確認不要）。
- **`git push`・`docker build`/`push`・Railway/Fly.io等への実デプロイ・本番相当DBへのマイグレーション実行**: どのサブエージェントもオーケストレーターも一切実行しない。必要になった場合は、**実行前に必ずAskUserQuestionまたは平文で確認を取ってから**、承認された範囲だけを実行する。
- デプロイ先（Railway/Fly.io）の選定はコード化されたタスクにしない。実際にデプロイが必要になった時点でユーザーに確認する。
